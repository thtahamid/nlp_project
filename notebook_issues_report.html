Notebook 05 — Qwen2.5-VL Fine-Tuning

CriticalNB05 All tokens used as labels — loss computed on prompt, not just assistant response

In Cell 7, inputs['labels'] = inputs['input_ids'].clone() clones every token including the system prompt, user message (with chat template tokens), and the assistant response. The standard supervised fine-tuning practice is to mask prompt tokens with -100 so the loss is computed only on the assistant response.

Iterate through message roles and set label=-100 for tokens belonging to system and user messages. Only assistant message token-positions should retain their original id as the label.

Impact: Model learns to predict its own prompt — wasted capacity, lower effective learning rate on actual target, potential output degradation.

HighNB05 Overfitting visible but only caught at epoch-end due to eval_strategy='epoch'

The training output shows training loss decreasing (1.63 → 1.45) while validation loss increases (1.63 → 1.64) — a textbook overfitting signal. With eval_strategy='epoch', the team only discovers this at the boundary of each epoch — too late to trigger early stopping or LR adjustment mid-epoch.

Set eval_strategy='steps' with eval_steps=50 (or similar), use EarlyStoppingCallback(patience=2), and enable load_best_model_at_end=True.

Impact: Unnecessary training compute; final checkpoint is worse than an intermediate one (epoch 2's VLoss is lower than epoch 3's).

MediumNB05 Deprecated warmup_ratio and logging_dir

Warnings "warmup_ratio is deprecated and will be removed in v5.2" and "logging_dir is deprecated" appear at runtime. While training proceeds, future Transformers versions will reject these parameters outright.

Switch to warmup_steps (compute as int(total_steps * 0.1)) and configure TensorBoard via TENSORBOARD_LOGGING_DIR env var.
Impact: Code will break in Transformers ≥ 5.2.
MediumNB05 DataCollatorForSeq2Seq — slow list-of-arrays tensor creation

Pytorch warning: "Creating a tensor from a list of numpy.ndarrays is extremely slow." The dataset returns mixed Tensor/numpy objects that force the collator to upcast via python list. Batch construction is slower than it could be.

Ensure every __getitem__ returns torch tensors for all values; pre-stack numpy arrays within the dataset using np.array() before tensor conversion.

Impact: Slower per-batch overhead; can add 5-10% to total training time on large datasets.

MediumNB05 Misleading adapter size cell output

The save cell prints "Training complete! Adapter size: 2.3G" — this is not the LoRA adapter alone; it includes the ~2.3 GB saved checkpoint contents (optimizer state, etc. despite save_total_limit=2). Earlier in the doc they note the adapter should be ~380 MB.

Post-save, run du -sh $OUTPUT_DIR/adapter_model.safetensors to report true LoRA weights size.

Notebook 06 — Qwen2.5-VL Evaluation

CriticalNB06 JSON prefix injected twice — before generation and post-generation

Cell 18 first does text += json_prefix (appends {"transcription":" to the prompt so the model generates value"}). Then after generation it does generated = json_prefix + generated. Final generated string: {"transcription":"{"transcription":"value" — a nested/duplicated JSON prefix that parse_output() would parse as a syntax error or misread.

Remove one of the two. Either (a) prepend before generation only and clamp output with stop_strings, or (b) prepend after generation only but then don't guide via prefix. Option (a) is the common correct pattern.

Impact: parse_output() may fail or extract buried valid JSON; observed CER=0% valid_json=100% suggests parse-extraction is working on outer wrapper only, but downstream scoring can be subtly corrupted.

HighNB06 Prediction identical across many worst samples — model hallucinating fixed phrase

Top-5 highest-CER samples all have the same prediction: "الصينية، وهم يدعونها باللغة الصينية..." regardless of the actual reference text (تأشيرة, جميلة, الصنيون...). This is a degenerate output from the LoRA adapter — the model has defaulted to outputting a single memorized phrase when uncertain.

Investigate dataset quality; consider more LoRA target modules, more epochs with stronger regularization (lora_dropout 0.1+), or switching to RSLoRA. The all-prefix-forcing may contribute — remove extra leading token bias.

Impact: Average CER ~1.28 is inflated by catastrophic outliers. Without them, average CER could be ~0.95.

HighNB06 Evaluation measures agreement with GPT-5.4-mini — not against human ground truth

All ground-truth references were generated by gpt-5.4-mini during dataset construction. Evaluation metrics thus quantify how well the fine-tuned model agree with another LLM's outputs, not how accurately it performs Arabic handwriting transcription. This conflates "learning GPT-5.4's distribution" with "being correct".

Collect a small human-annotated gold set (even 20-50 samples) to compute a secondary "real accuracy" metric. Report both: "agreement with GPT reference" vs "gold-accuracy".

Impact: Reported numbers have no bearing on actual task performance; the project cannot claim handwriting recognition improvement.

MediumNB06 No Arabic text normalization before CER/WER computation

Arabic orthography has equivalent characters that differ in Unicode code-points (alef with/without hamza: ا/أ/إ/آ, ta-marbuta vs ha: ة/ه, ya vs alef-maqsura: ي/ى, diacritics/tashkeel). None are NFC/NFKC normalized; a single variant swap inflates CER artificially.

Apply unicodedata.normalize('NFC', text) (or more aggressive NFKC) before computing CER/WER. Optionally strip diacritics (Tashkeel) before comparison.

Impact: CER/WER may be overestimated; exact match rate may be 0% only due to encoding variance.

MediumNB06 Exact-match rate is 0.0% despite reasonable CER

With avg_CER ≈ 1.28 and many predictions visually close to references, exact-match = 0% is overly pessimistic. Character-level diacritics, trailing whitespace, or minor punctuation differences nullify this metric without reflecting real usability.

Report both strict exact-match and a tolerant match (e.g., after Unicode normalization, diacritic-stripping, case-folding).
LowNB06 WER=1.0 for most samples indicates word-level split mismatch

Arabic has clitics and attached pronouns pre-tokenized as whitespace-attached by GPT but tokenized differently by the model — even a single character edit splits a word, producing WER=1.0 for samples that "look" very close, reducing metric informativeness.

Impact: WER metric is a binary indicator dominated by whitespace boundaries, not useful for ranking sample quality.

Notebook 08 — Qwen3.5-9B Fine-Tuning

CriticalNB08 Model Qwen/Qwen3.5-9B does not exist on Hugging Face

No repository named Qwen/Qwen3.5-9B exists on Hugging Face as of Spring 2026. The repo doesn't load Qwen3 series official releases, nor Qwen3-VL or Qwen3.5-Entry. The notebook will fail at Qwen3_5ForConditionalGeneration.from_pretrained() (or even at snapshot_download if the name resolves to a missing repo). The entire pipeline is unreachable.

Switch to a real, supported model — likely Qwen/Qwen2.5-VL-7B-Instruct (already used in NB05) or Qwen/Qwen2.5-7B-Instruct+ VL processor, depending on task. If the intent is next-gen, use the actual released Qwen/Qwen3-8B with appropriate class (e.g., Qwen3ForCausalLM / Qwen3VLForConditionalGeneration if Vision-Language).

Impact: Notebook crashes immediately — zero progress possible without fixing.

CriticalNB08 Qwen3_5ForConditionalGeneration is not a valid Transformers class

No such class exists anywhere in Hugging Face Transformers. Even if a model were loaded, the code would raise ImportError. There's no Qwen3_5... class in HF transformers as of 2026. The existing classes are: Qwen2ForCausalLM, Qwen2_5_VLForConditionalGeneration, Qwen3ForCausalLM, etc. The "3.5" naming is fabricated.

Use correct class for chosen model — e.g. Qwen2_5_VLForConditionalGeneration for VL tasks, Qwen3ForCausalLM for Qwen3 text-generation.
CriticalNB08 Vision inputs silently dropped — HTR model fed text-only to vision-language dataset

Cell 7 calls processor(text=text, return_tensors='pt', ...) with NO = images parameter. The Arabic HTR dataset contains base64-encoded page images — those images are entirely discarded before processing. The model trains on (chat_template, transcription) text only. Even if Qwen3.5-9B existed, the vision signal is lost.

Implement the extract_images() and pass to processor exactly as Notebook 05 Cell 7 does. Without image inputs, "fine-tuning for Arabic HTR" is meaningless — the model learns prompt completion, not vision-language transcription.

Impact: The whole fine-tuning objective collapses — model never sees handwriting images.

HighNB08 padding='max_length' pads every sample to 8192 tokens

Unlike NB05 which uses DataCollatorForSeq2Seq with dynamic padding, NB08 uses padding='max_length' — every batch element allocates an 8192-length tensor regardless of true sequence length. This is dramatically slower and wastes GPU memory (24 GB A10G), making training infeasible.

Use padding=True (dynamic) with a DataCollatorForSeq2Seq, matching NB05 pattern.
HighNB08 No run naming / checkpoint isolation

OUTPUT_DIR = Path(PROJECT_ROOT) / 'models' / 'lora_adapter' — same path for every run. No RUN_NAME versioning unlike NB05's run-N scheme. Re-runs will overwrite prior adapters with no history.

Mirror NB05's RUN_NAME config and output_dir = f'models/lora_adapter/{RUN_NAME}' structure.

processor(text=text, return_tensors='pt') — no images. Same fatal NB08 issue carried into evaluation. The model "sees" only the chat prefix, never the handwriting page. Every prediction is faith-authored text — no vision signal. Equivalent to evaluating a random text decoder.

HighNB09 max_new_tokens=512 hallucination budget — 4x larger than needed

Arabic transcriptions average ~5-20 words; 512 output tokens invite massive over-production. Combined with no stop_strings, the model can generate unlimited trivia.

Set max_new_tokens=128 (matching NB06) and add stop_strings=['\"'] via tokenizer.
HighNB09 temperature parameter supplied but unused

model.generate(... temperature=0.7, do_sample=False) — setting do_sample=False (greedy) makes temperature a dead parameter. The generation mode is greedy, but the config implies stochastic sampling to a reader. This is confusing and masks true generation behavior.

Remove temperature when do_sample=False.
MediumNB09 Hand-rolled difflib-based CER/WER instead of jiwer

While difflib's SequenceMatcher implements O(ND) algorithms that approximate Levenshtein distance ratios (giving same results as jiwer), the implementation is non-standard and harder to audit. Also, jiwer handles Arabic-specific tokenization refinements and provides word-level isolation that difflib does not.

Use jiwer.cer and jiwer.wer (from NB06) for standardization and easier comparison.
MediumNB09 KV cache not enabled for inference

Unlike NB06 which does model.config.use_cache = True, this notebook omits the KV cache toggle. Generation is slower (≈linear-per-token instead of constant-per-token).

Set model.config.use_cache = True, or pass use_cache=True in generate args.

Use environment variable or relative path like NB05/ .

Cross-Cutting Issues — Evals, Evals During Training, Metrics

HighCROSS Training monitors only loss — no CER/WER during training

Despite the downstream evaluation using CER/WER / exact-match as business-useful metrics, training only monitors scalar loss. Loss does not correlate well with CER/WER (e.g., small loss reduction can still yield high CER if the model overfits to prompt tokens). There's no way to see "is transcription quality improving?" inside the training loop.

Install a custom Trainer callback that computes CER on a small eval subset every N steps (on_log). Report via W&B/Trackio.

Impact: Impossible to early-stop on actual quality signals; project can't optimize for its stated metric.

HighCROSS report_to='none' — no experiment tracking

TrainingArguments(report_to='none') disables all logging. No W&B, TensorBoard, or HF-Trackio runs. Training is non-reproducible without external logging — only stderr output is saved, which is ephemeral.

Enable report_to='trackio' with a proper run_name and project. Include Trackio Space ID if available.
MediumCROSS LoRA task_type 'CAUSAL_LM' may silently ignore VL projection losses

For vision-language models, LoRA is applied to text-only submodules (q/k/v/o/gate/up/down). The vision tower and visual-aligned adapter layers are not LoRA-targeted, which is expected. However, the task_type='CAUSAL_LM' flag is not a concern here since we only LoRA the decoder. No VL-specific adapter layers are modified, so purely linguistic writing must adapt entirely through the LoRA-injected attention.

Document why certain VL layers are excluded; optionally add LoRA to VL-bridging tensors.
MediumCROSS No load_best_model_at_end=True and no early stopping

NB05 uses save_total_limit=2 but does not set load_best_model_at_end=True. After training, the loaded adapter is the final (worse) checkpoint, not the best. NB06 hand-selects checkpoint-1120 as a workaround, but this is manual and fragile.

Add load_best_model_at_end=True and metric_for_best_model='eval_loss' to TrainingArguments. Add EarlyStoppingCallback.
LowCROSS do_sample=False in eval but temperature varies (0.1 vs 0.7)

0.1 is used in NB06 (but do_sample=False!); 0.7 is in NB09 (same issue). Temperature is non-informative when sampling is disabled. The reported numbers do not capture stochastic variance at all.

Remove temperature entirely when do_sample=False.
